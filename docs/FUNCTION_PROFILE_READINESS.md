# 函数数据画像接入与研究可行性检查

日期：2026-10-18（America/Los_Angeles）。检查对象：首批5条画像及当前`stat_rag`实现。结论：**画像构成可用的研究准备，但尚未进入运行流程，不能声称已改善质量、检索成本或token消耗。**

本次为代码检查和离线兼容性探针，不是正式对比实验；没有模型API调用，也没有执行R函数。实测输出、所检查提交及文件哈希保存在[审计记录](../results/function_profile_readiness.json)。画像仍为pending_user_review，未扩批、未修改前两轮冻结实现或结果。

## 当前确实增加了什么

- 4个保留函数的输入要求来自文档，有逐项依据和推断标识；排除函数单独留档。
- 共24条带条件的判断，能为参数和接口相关的适用性判断提供材料。
- unknown、推断和文档歧义分开保存，可以避免把未找到要求误写成无限制。
- 区分required、supported、behavior和warning，为以后区分硬冲突、支持范围和提醒提供结构。

这些是标注和解释能力方面的进展，尚未转化成路由效果。

## 实现检查

| 检查项 | 观察 | 影响 |
|---|---|---|
| 数据加载 | `Corpus`仍只加载`studies.json` | 运行流程没有读取新函数画像 |
| 需求解析 | 4条PCA、均值比较、中心化和聚类探针均落入unknown主题 | 现有解析器针对上一轮合成研究卡，不识别这些新任务 |
| 条件判断 | `compare`采用逐字段字符串相等判断 | 不理解类型包含、长度关系或参数条件 |
| 未知语义 | 字面量unknown与unknown被判为applicable | 直接展平接入会错误确认未知条件 |
| 类型语义 | numeric_or_complex与numeric被判为conflict | 支持集合与实际类型不能直接做字符串相等比较 |
| 证据与生成 | 仍验证研究卡条件并摘录结果 | 没有数据检查、函数执行和结果解释验证链路 |

两个比较器探针是对新接入方案的兼容性检查，超出了原比较器的冻结输入约定，**不据此否定前两轮实验结果**。4条解析探针也不代表通用解析准确率。

本次在当前PATH中未找到Rscript；这不证明机器上没有安装R。函数执行层仍需单独配置和验证，读取文档本身不要求运行R。

## 画像仍不足以直接执行的地方

1. `applies_when`是声明性标签，尚非可执行条件；有些目标如`center_or_scale_parameter`需要进一步拆成真实参数条件。不能把条件不生效当作数据不符合。
2. `at_least_k`、`ncol(x)`等是描述性值，需要变量绑定与关系运算。应保留原始标注，在单独适配层规范化，不能静默改写证据。
3. 支持范围、行为、警告和硬要求具有不同作用。不能把行为描述统统转换成负向排除条件；推断的要求也不能未经验证就当作可靠硬门槛。
4. 4个保留函数的分布族均为unknown。当前材料支持接口和部分输入条件研究，不足以支撑“已掌握完整分布适用性”的说法。
5. 需要实际输入侧信息，如变量类型、形状、缺失情况，以及来自用户或研究说明的设计信息。函数侧画像不能替代它们。
6. 文档版本差异和参数文字歧义仍未解决；不得把有歧义的条目自动编译为阻断规则。

## 能检验的下一步

建议先在现有样例上做12–20个小案例，验证条件判断语义，不急于扩大函数库。每例明确函数、方法、参数、数据事实及预期处置，并附判断依据。至少覆盖：

- 条件满足：确认文档中的具体输入要求，但不宣称所有统计假设已验证。
- 条件冲突：例如已指定配对调用而两输入长度不一致，阻止该调用配置；不得擅自改为另一种分析。
- 条件未知：缺少某项必要信息时说明缺口，决定澄清或进一步检查。
- 条件不生效：参数分支未启用时，不应用该分支约束。
- 参数行为变化：缺失值处理或缩放行为随接口/参数变化。
- 画像不确定：文档未知、来源歧义和推断条目不能自动变成适用或不适用。

对应工程增量应限于：画像适配器、输入事实表示、带条件的兼容性判断、可解释决定与预算记录。先保留原始画像和原实验模块，新增独立流程。

有必要的信息未知时再澄清；不应要求画像里所有未知都先消失。判断的是当前任务和配置所需的条件。条件不生效、文档未说明、实际数据未提供、文档相互冲突应分别记录。

## 怎样判断有没有研究增益

目前4个保留函数分别对应均值检验、PCA、聚类和中心化缩放，任务差异明显。仅用它们比较选函数正确率，主题描述可能已经足够；这5条原本就是标注样例，不是检索基准。

条件语义检查通过、标注口径确认后，再加入同一任务下的候选方法/配置，构建近似主题但输入条件不同的案例。普通全信息路由与边界方法必须读到相同的文档、画像和输入信息，获得相同预算和检查工具。

需要分开回答三个问题：

| 研究问题 | 建议对照 | 衡量内容 |
|---|---|---|
| 结构化画像是否有用 | 相同原始文档 vs 文档加可追溯画像 | 错选、漏选、解释质量及画像构建/读取成本 |
| 显式边界是否有额外作用 | 完整画像普通兼容性路由 vs 条件边界判断 | 不兼容配置率、可用配置误排率、未知误判率 |
| 自适应行动是否省成本 | 固定检查策略 vs 有预算的按需检查/澄清 | 同等质量下的检查、调用、token及端到端耗时 |

执行成功仅是后续评价的一部分，还需检查分析目标、参数及结论是否正确。没有报错不能作为统计有效性的完整金标。离线案例只用于开发验证；正式比较继续遵守用户要求，使用一致在线模型并计入路由与检查费用。

建议设置继续投入的门槛：先证明不再误判未知、正确处理参数分支及支持集合；再证明优于信息和预算相同的普通路由。若仅胜过主题描述基线，应将收益归于画像信息；若后续同信息对照仍无优势，应接受负向表示独立贡献不足的结论，而不是继续扩大弱基线差距。
